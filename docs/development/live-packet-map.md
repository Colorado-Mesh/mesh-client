# Live packet map

The existing Map panel has a **Live traffic** view for MeshCore and Meshtastic. Reticulum keeps its existing map. The standalone development preview is `/live-traffic-preview.html` on the Vite server; it uses the same panel, starts without packet observations, and can connect explicitly to a real regional feed. There is no generated or simulated traffic in either entry point.

## Sources and regions

Local traffic uses the client's existing packet logs and node positions. MeshCore's **Traffic source** dropdown selects **Local radio**, **Regional Beacon**, or **Regional CoreScope**. Choose a regional preset or enter a custom map URL and click **Connect**; connection is read-only, never automatic, and sends no local radio packets, node directory, messages, or location. Each provider's URL is saved separately. Within the running app, each protocol retains its Overview/Live traffic choice, source, connection, feed region, filters, map viewport, and floating feed state when navigating to other panels or protocols. Overview also suspends the live drawing without disconnecting a regional session. Explicit Disconnect/Cancel, changing the source, disabling the protocol, or closing the app ends that session; reopening the app still requires Connect. These public feeds need no API key; this implementation does not accept administrator keys or authenticated private feeds. Meshtastic retains its local traffic source because these two regional APIs carry MeshCore observations.

Beacon region subscriptions come from that server's region directory and also scope node and observer REST requests. CoreScope regions use the server's IATA directory; its global WebSocket stream is filtered locally against explicit observer membership. Unknown membership is excluded when a region is selected. Map region presets and Current viewport filter the display independently. The MeshCore local transport scope filter is separate from geography and is hidden for regional sources.

Colorado's public deployment supports `packetObservation` and `channelMessage`. Message bodies are joined to observations by exact packet hash, whether text arrives before or after the observation. Reports with the same packet hash share one feed row and a union of retained directed branches, with CoreScope collision estimates labeled separately. Shared edges draw once; newly observed branches animate without replaying old branches. Separate source sessions never share grouping or animation identities. The popup shows a short excerpt; selection shows the full bounded text and separate branch links. Encrypted or unavailable text is labeled without inventing content. No messages are added to the normal chat store.

Local MeshCore repeats use the full path-independent payload and routing context as their grouping identity, rather than a short CRC alone. Meshtastic grouping also verifies packet identity and exact payload content. Already decoded Meshtastic text can appear in the feed; MeshCore ciphertext is not matched to chat messages using timing heuristics. The configured self position is available to local receiver geometry, including the existing static-location override.

The verified Beacon presets are Colorado Mesh, MeshCore Canada, Palouse Mesh (Pacific Northwest), Meshat (Sweden), Atviras Tinklas (Lithuania), EastMesh (Australia), MeshCore Catalunya (Spain), MeshMapper (worldwide), and BSmesh (Braunschweig, Germany). Older Palouse and EastMesh servers provide resolved paths with fewer observer/repeat fields; missing endpoints remain unknown.

CoreScope presets are Boston (New England), Chicagoland, Rhineland (Germany), Meshat (Sweden), EastMesh (Australia), Atviras Tinklas (Lithuania), and Palouse Mesh (Pacific Northwest). These use separate API endpoints from those communities' Beacon deployments. Selecting a preset does not connect automatically. The catalogs are in `src/renderer/lib/map/beaconPresets.ts`; public service availability can change.

Beacon uses its [public API contract](https://github.com/MeshCore-Beacon/beacon-docs/blob/main/docs/api-contract.md), including `/api/v1/` directories and a configured `/ws` subscription. CoreScope uses `/api/nodes`, `/api/observers`, `/api/config/regions`, and its root WebSocket endpoint. CoreScope broadcasts on connection without Beacon's configuration frames. Public plaintext arrives inside packet observations; no per-channel history is fetched.

## Display and route fidelity

Control packets without an identified sender show their purpose: **Node discovery request**, **Node discovery response**, or **Control packet** when the subtype is unavailable or unrecognized. These descriptions do not identify the sender. Sender identity never falls back to a receiver or route hop. The CONTROL category remains unchanged for filtering. Colorado Beacon's current live observations omit control payloads and subtypes, so they use the generic label; subtype data is used when a source supplies it without fetching per-packet detail requests.

Packet motion illustrates observation order, not radio propagation speed. Each observation retains its original contiguous hop runs. Unknown, ambiguous, or unlocated hops break paths, including when the same node occurs on both sides of a missing hop. MeshCore direct paths are not presented as completed traversals. Meshtastic only draws a source-to-client segment for a known direct RF reception; multihop and MQTT observations do not invent intermediate hops or a local receiver.

CoreScope shares transmission `raw_hex` across observations. Each report's validated `path_json` supplies its own hop order. Server-resolved candidates must match those on-air prefixes and a located full key in the directory. When the server chooses among colliding prefixes, the route is labeled **Server-estimated route**; the client does not invent a nearest-node choice. Missing, unlocated, or mismatched candidates remain gaps. Reusing the shared raw packet path for every receiver would erase real branches and draw incorrect routes.

CoreScope's `timestamp` and `first_seen` describe the transmission's first appearance, not necessarily this observer's receipt. Live retention uses local feed arrival time so later receiver reports can extend the same packet's graph; the original first-seen timestamp is retained as provenance. Timing is illustrative, including when a server batches reports.

The animation follows [CoreScope's packet travel behavior](https://github.com/Kpa-clawbot/CoreScope/blob/master/public/live.js): a 660 ms linear hop, a growing line behind the packet, an outlined leading dot, an arrival pulse, and a short fade after arrival. Shared edges animate once; new branches follow their known predecessors. Normal playback reveals only traveled edges and removes completed trails. Selecting a packet shows its retained graph for inspection. The scheduler and renderer are implemented locally for the client's observation model and bounded canvas.

Scroll zoom uses half-level steps and a lower wheel sensitivity; explicit plus/minus controls remain available. Map details and source configuration expand on demand. The panel and map shrink to their available container height, including at the app's 150% font setting, so expanded controls do not force the feed below the window.

Current viewport filtering, markers, and packet motion follow the visible wrapped world. Links across the dateline take the short route instead of drawing across the whole map.

Source settings preserve the chosen server region when closed, expose Disconnect or Cancel while a feed is active, and support Escape with focus returning to the settings button. Geographic **Map area** is independent of the server's **Feed region**. The fit button uses current traffic when available; incoming packets do not pan the map automatically. Existing **Show on map** actions return to Overview and use its normal focus controller.

The transparent feed is movable by its grip or arrow keys (Shift increases the step). Expansion grows upward from its bottom anchor; collapse restores the compact bar there, including after temporary viewport clamping. Reset restores the default lower-right position. Pause freezes displayed events and inspection geometry and stops animation while new input remains bounded. Resuming does not replay paused traffic.

The dark map uses OpenStreetMap raster tiles with a neutral dark filter applied only to tile images. It requires no CARTO key. See [offline maps](offline-maps.md) for tile-provider caching and download restrictions.

## Resource bounds

- One animation canvas, at most 64 admitted edge flights, drawing at most 60 times per second while motion is active, device pixel ratio capped at 1.5.
- Up to 128 displayed edges per selected graph, 400 memoized node markers selected from the viewport, 32 inspector location chips, and 25 feed rows. Truncated inspection lists indicate the remainder. Selected and active endpoints have marker priority. Completed animation trails fade out instead of leaving persistent recent graphs.
- At most 200 recent observer reports retained; live display expires reports after 60 seconds. This is not a guarantee of 200 distinct packets. Grouping retains the resolved observed and server-estimated edges in those reports, preserving route uncertainty; the canvas applies its own display bound.
- Regional renderer updates batch at most four times per second. Their publication timer stops while the map is inactive or the document is hidden; the single regional connection continues collecting only its bounded recent reports. Inactive maps unmount Leaflet, markers, the feed list and animation canvas while retaining the lightweight controller and source form. Returning restores the viewport and does not replay retained traffic. Animation stops while paused, hidden, idle, or reduced motion is enabled.
- Native requests have size/time limits, public-address validation, pinned DNS, no redirects or credentials, bounded WebSocket input, and reconnect backoff. Each snapshot attempt cancels sibling directory requests on failure. Unrelated CoreScope regions do not consume the selected region's forwarding allowance; global parsing limits still apply. Reconnect refreshes directories and, for Beacon, recent public messages; CoreScope fetches no message history. Observations missed during the gap are not replayed.
- Directory snapshots cap at 5,000 nodes and 1,000 observers. The UI indicates a limited directory when those bounds are reached. Selecting a Beacon region scopes directory requests; CoreScope keeps a bounded global directory because only observer membership filtering is verified for its live stream.
- The loopback-only Vite regional bridge reuses the native read-only client for both providers. It exists only during development and preserves the browser's external tile fallback.

These are implementation limits, not a measured performance comparison with CoreScope. MeshCore BLE reception has been exercised in the native app; physical Meshtastic radio behavior still needs a real-device review.
